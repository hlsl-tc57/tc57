### 6.1 Normative consensus PRs

The only open normative consensus PR was [Math.GeneralFunctions](https://github.com/hlsl-tc57/tc57/pull/207).

**Gregory Roth** (Nvidia) expressed a lack of confidence in where the prose describes smooth step, bringing up that there are open questions regarding how it is defined. He suggested removing that section to prevent his concern from blocking the rest of the pull request, and adding the smooth step piece at a later date. Keith had left a series of comments, all primarily targeted at editorial changes such as typos; Gregory provided easy-to-apply suggestions on the PR for many of them. Gregory also brought up fused vs unfused operations, and contested the text that described fused operations as higher precision. Chris agreed and provided [a tweak to the language](https://github.com/hlsl-tc57/tc57/pull/207#discussion_r4261099286). The next [comment](https://github.com/hlsl-tc57/tc57/pull/207#discussion_r4257102738) reviewed was one from Keith regarding the “precise” keyword, and its guarantees (or lack thereof). Chris explained that “precise” actually more accurately accomplished consistency over precision. The committee came up with [replacement text](https://github.com/hlsl-tc57/tc57/pull/207#discussion_r4261161565) to clarify.

The committee worked through the language and approved the PR to be merged.

### 6.2 [Should structs with mutable fields be allowed in constant resources?](https://github.com/hlsl-tc57/tc57/issues/216)

Chris proposes that HLSL error when a struct containing a mutable member is inside a resource that cannot be written to, such as constant buffers, texture buffers, or non-writable structure buffers. This can be a protective measure for both the user experience and compiler resilience. There is no C++ prior art to rely on, because C++ has no notion of memory that is truly read-only. **Hai Nguyen** (Nvidia) was interested in what the structure of that error message would be, Chris proposed something to the effect of “you cannot put a structure with a mutable field inside a read-only resource”.

Keith & **Greg Mitrano** (Microsoft) were trying to figure out how to do this without then resulting in a user making a copy of that struct to run some operation on it, leading to two copies of a struct in play.

The committee explored producing the error as a compilation error, but lacked confidence that the error would be statically knowable in the long-term development of the language, such as implementing references.

Ultimately, Hai expressed an appreciation for this suggestion from the perspective of language purity, but suggested that pragmatically it was not an ideal outcome for HLSL developers without HLSL gaining other planned features such as conversion functions.

**Helena Kotas** (Microsoft) initially suggested that this should at least be a warning, even if the committee wasn’t completely sold on throwing an error.

After some additional back and forth, Chris pointed out that due to the fact that const member functions is a new feature, existing code wouldn’t be broken by making this an error. The committee then quickly reached consensus on making it an error.

### 6.3 [Initializers on groupshared values](https://github.com/hlsl-tc57/tc57/issues/217)

DXC ignores initializers on group shared values, but only sometimes the compiler provides a warning—others it ignores them silently. Chris proposes introducing some consistency here, aligning ignored initializers on group shared memory with ignored initializers on cbuffer values (i.e. error).

There is a viable alternative Chris provided—making it work. The drawback here is that it could impact existing code unexpectedly. Gregory Mitrano shared that there is some hardware that can initialize to 0, so this may be more than a basic quality-of-life improvement. Chris suggested making a change for the purpose of that accommodation might be something Microsoft & Kronos may choose to standardize separately.

Overall, the committee is aligned on this being illegal. Chris will prep a PR for a future meeting.

### 6.4 [Add 0/1 swizzle syntax](https://github.com/hlsl-tc57/tc57/issues/219)

There’s currently a proposal ([0011](https://github.com/hlsl-tc57/tc57/blob/main/proposals/0011-strict-initializer-lists.md)) to change initialization and remove the ability to append a literal value to the end of a vector in order to change its dimension or add a homogeneous coordinate. It’s not currently planned for 202x, but at any point it where to be added, Gregory Roth proposes swizzle syntax, which could restore some developer ergonomics lost by 0011’s strictness.

There was support in the committee to pursue this in either 202x or 202y and independent of 0011, specifically allowing placement a 0/1 in the first element for non-literals.
