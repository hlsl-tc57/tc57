## 6.2 Open issues regarding language changes

### 6.2.1 Overview

The committee reviewed open issues which do not fall clearly on one side or the other of “defect” vs “proposal”. Part of this tension is how to handle distinction between specification text and the reference implementation. The chair sought consensus on how to handle issues that are both a gap in the specification and a defect in reference behaviour.

### 6.2.2 HLSL Enumerations ([hlsl-tc57/tc57#190](https://github.com/hlsl-tc57/tc57/issues/190))

This issue acknowledges that between feature introductions to DXC, C++ made meaningful changes causing divergence in HLSL enum declaration. The committee decided to treat this as a defect.

### 6.2.3 Include all ways of declaring a cbuffer ([hlsl-tc57/tc57#194](https://github.com/hlsl-tc57/tc57/issues/194))

There is a gap in [proposal 0005 (accepted)](https://github.com/hlsl-tc57/tc57/blob/main/proposals/0005-cbuffer-contexts.md) regarding two additional manners in which to declare a cbuffer. The chair suggested this is an intended but thus far unwritten aspect of the specification, as opposed to an oversight, and considers it a part of the roadmap.

### 6.2.4 Refine language about matrix subscripting ([hlsl-tc57/tc57#195](https://github.com/hlsl-tc57/tc57/issues/195))

This issue concerns a gap in [proposal 0006 (accepted)](https://github.com/hlsl-tc57/tc57/blob/main/proposals/0006-restricted-unbound-arrays.md), where an edge case of invalid matrix subscript is not thoroughly described. The committee opted to treat it as a defect.

### 6.2.5 Initialized unsized array declarations ([hlsl-tc57/tc57#196](https://github.com/hlsl-tc57/tc57/issues/196))

The proposed solution section of [0006](https://github.com/hlsl-tc57/tc57/blob/main/proposals/0006-restricted-unbound-arrays.md) mentioned allowing unsized arrays for resources and also for arrays where the initialization implied the size, but the latter is missing from the accepted design. The committee reached consensus to treat this as a defect.

## 6.3 How should we define HLSL strings? [(hlsl-tc57/tc57#200)](https://github.com/hlsl-tc57/tc57/issues/200)

HLSL currently handles strings inconsistently. Chris Bieneman (Microsoft) proposes that strings are specified as an intangible type, and in the future that printf is added to the standard. The committee reached consensus to pursue this further, and to treat this as a defect.
